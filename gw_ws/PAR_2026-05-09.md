# Friend Maker ESP32 Switch Controller Project - PAR Summary

## 1. Project Understanding

Problem:
The original project is an ESP32-based automation tool for drawing in "Tomodachi Life / 朋友收集梦想生活" by emulating a Nintendo Switch controller. The user needed to understand how it works without frontend/backend experience.

Action:
Read the project structure and explained the full chain:

- Desktop UI imports and processes an image.
- UI generates drawing commands.
- Commands are sent over serial to ESP32.
- ESP32 translates commands into Switch controller inputs.
- Switch receives those inputs as controller actions and draws in-game.

Result:
The user understood that the project is not "image sent directly to Switch"; it is a serial-command-to-controller-input automation chain.

## 2. ESP32-S3 Compatibility Problem

Problem:
The user had an ESP32-S3-N16R8 board. ESP32-S3 supports BLE and USB native device, but does not support Bluetooth Classic. Switch controller wireless emulation needs Classic Bluetooth HID, not BLE.

Action:
Checked current Switch controller requirements and explained:

- BLE-only ESP32-S3 cannot emulate a wireless Switch Pro Controller through Classic Bluetooth.
- The ESP32-S3 can still emulate a controller through USB HID because it has native USB.
- Hardware plan:
  - UART Micro-USB port to PC for serial and flashing.
  - Native USB Micro-USB port to Switch Lite through USB-C OTG.

Result:
The project route changed for ESP32-S3 from Bluetooth to USB HID. This avoided the Classic Bluetooth limitation.

## 3. Switch Lite USB HID Feasibility

Problem:
The user had a Switch Lite, which has only a USB-C port and no dock USB-A port. The question was whether a direct OTG connection could be recognized as a wired controller.

Action:
Studied similar USB Switch controller projects and built a minimal ESP32-S3 USB HID demo in `gw_ws`.

Result:
The user confirmed the demo worked. Switch Lite recognized the ESP32-S3 USB HID controller through OTG, and basic inputs worked.

## 4. Environment Management

Problem:
PlatformIO was initially installed into the user's Anaconda base environment, causing Python dependency conflicts:

- `httpcore 1.0.2` required `h11<0.15`, but `h11 0.16.0` was installed.
- `pyOpenSSL 24.0.0` required `cryptography<43`, but `cryptography 45.0.7` appeared.

Action:
Explained that PlatformIO should use VS Code PlatformIO's isolated environment:

```text
C:\Users\86181\.platformio\penv\Scripts\pio.exe
```

Also documented not to modify Anaconda base casually.

Result:
The user moved PlatformIO work to the VS Code PlatformIO environment and stopped relying on Anaconda base for embedded work.

## 5. USB HID Integration Into Main Project

Problem:
The `gw_ws` USB HID demo worked, but the real Friend Maker firmware still used the original controller transport structure. The user wanted the main project to support the ESP32-S3 USB route while preserving original Bluetooth support.

Action:
Integrated USB HID into the main firmware:

- Added `switch_hid_gamepad.cpp/.h`.
- Added `usb_hid_controller_transport.cpp/.h`.
- Added PlatformIO environment `esp32s3_usb_switch`.
- Updated `main.cpp` transport selection.
- Updated UI status logic to recognize `usb-hid-switch`.

Result:
The ESP32-S3 route worked in the main project. The user successfully imported an image and completed a drawing through USB HID.

## 6. Desktop UI / Serial Issues

Problem:
The user had trouble opening serial monitor and sending manual commands. Later, the web UI sometimes showed stale "connected" state while the controller had already dropped.

Action:
Explained how PlatformIO monitor input works and adjusted UI behavior:

- Status is refreshed before test actions.
- Ordinary buttons are blocked unless the controller state is truly ready.
- L+R pairing is allowed earlier only when the connection has reached an appropriate Bluetooth stage.

Result:
The UI stopped blindly sending commands based on stale green state. This made failures more honest and easier to diagnose.

## 7. Electron / npm Issue

Problem:
`npm install` failed during Electron native dependency rebuild because Windows lacked Visual Studio C++ build tools:

```text
node-gyp failed
Could not find any Visual Studio installation to use
```

Action:
Explained that the failure came from native module rebuild, especially `@serialport/bindings-cpp`, and that web UI could still run if dependencies were already usable.

Result:
The user continued using the existing UI environment without further polluting Python/PlatformIO environments.

## 8. ESP32-WROOM Bluetooth Route

Problem:
The user obtained an ESP32-WROOM board and wanted to try the original Bluetooth route. Initial tests were unstable:

- COM11 access denied when another process held the port.
- UI showed "broadcasting" or "connected" but Switch did not accept inputs.
- Logs showed:
  - `bt report skipped reason=not-ready connected=false paired=false`
  - `send-report status=1 reason=8 report=48`
  - `controller input report failed`

Action:
Investigated the Classic Bluetooth chain:

- Desktop UI sends serial commands.
- ESP32 parses sequenced commands.
- ESP32 sends Bluetooth HID reports.
- Switch sends HID output reports and subcommands.
- ESP32 replies to Switch subcommands.

Compared behavior with:

- `nullstalgia/UARTSwitchCon`
- `EasyConNS/BlueCon-esp32`

Result:
Confirmed the main risks:

- UI could mark connection ready too early.
- Auto reset could interrupt Switch handshaking.
- Bluetooth HID send-report congestion needed better handling.

## 9. Bluetooth Auto-Reset Race

Problem:
The UI automatically reset Bluetooth when the connection seemed stuck. Logs showed resets happening while Switch was beginning to authenticate or connect.

Action:
Changed UI recovery behavior:

- Do not auto reset during possible handshake.
- Show recovery guidance instead.
- Let the user manually reset when needed.

Result:
Fewer connection races. Logs became easier to interpret because fewer resets happened during Switch handshake.

## 10. Bluetooth Send-Report Handling

Problem:
ESP32 sometimes returned `OK` to the PC even though Bluetooth HID reports were congested or rejected.

Action:
Changed firmware behavior:

- Slowed idle report cadence.
- Increased congestion retry window.
- Explicit inputs wait for HID send-report callback when paired.
- Added diagnostic fields:
  - `bt_report_congested`
  - `bt_consecutive_send_failures`
  - `bt_input_report_submitted`
  - `bt_input_report_completed`

Result:
The firmware became more honest about failure instead of letting the UI believe a failed Bluetooth input had completed.

## 11. Pro Controller Pairing State

Problem:
ESP32 could send L+R and A in "Change Grip/Order", but after pressing A and leaving the page, all inputs stopped. This meant the connection was not a fully accepted controller session.

Action:
Found that the firmware was marking Pro Controller paired at `subcmd=0x30` / `reply3001`. Compared with UARTSwitchCon behavior and changed logic:

- `reply3001` alone is not treated as fully paired for Pro Controller.
- The firmware waits for later pairing-ready steps, especially the NFC/IR MCU style path.
- Added diagnostics:
  - `bt_intr_report_count`
  - `bt_last_intr_report`
  - `bt_last_intr_subcmd`
  - `bt_reply_count`
  - `bt_last_reply`

Result:
The UI no longer allowed normal buttons after only partial pairing. This exposed the true state instead of hiding it behind a false green status.

## 12. Bluetooth Address Mismatch

Problem:
The Switch kept repeating:

```text
bt_last_intr_subcmd=48/1/0
bt_last_reply=reply3001
```

This meant Switch repeatedly sent "set player lights" and did not proceed. The firmware's `reply02` still contained a fixed Bluetooth address that did not match the board's actual Bluetooth address.

Action:
Updated firmware:

- Runtime writes the actual ESP32 BT MAC into `reply02`.
- Logs `reply02_mac`.
- Cleans stale handshake counters on reset.

Result:
The Switch no longer received a self-reported controller address that contradicted the real Bluetooth connection address.

## 13. Serial ACK / Bluetooth Log Interleaving

Problem:
The serial output sometimes glued command ACK and Bluetooth logs together:

```text
OK cdabaINFO action=input-config...
```

This caused repeated malformed ACK warnings and retries.

Action:
Updated desktop serial parsing:

- Detects sequenced ACK at the beginning of a line.
- Splits embedded `INFO` / `WARN` device logs from the ACK.

Result:
The desktop command protocol became more tolerant of asynchronous Bluetooth logs.

## 14. Commercial-Style Reconnect

Problem:
After Switch reboot, ESP32 power cycle, and web UI restart, the controller could reconnect but sometimes lost usability after A. After manual reset it could stay stuck in broadcast. The user wanted behavior closer to a commercial Bluetooth Switch controller.

Action:
Implemented last-peer reconnect behavior:

- Store the last successful Switch peer address in NVS as `peer_addr`.
- Load it on startup.
- After HID app registration, schedule a delayed reconnect to the last Switch.
- Make `BT RESET LAST-PEER` prefer the saved peer.
- UI no longer treats pure `discoverable=true` as a reusable active connection.
- UI "connect" and "reset bluetooth" now use `BT RESET LAST-PEER`.

Result:
The user reported that selecting the serial port directly connected quickly and stably. Reconnect behavior became close to the desired commercial-controller style.

## 15. Final Stable State

Problem:
The user now has a stable version and wants to preserve it before doing detail-level changes.

Action:
Recorded this version as the `2026-05-09` stable baseline. The baseline includes:

- USB HID route for ESP32-S3.
- Classic Bluetooth route for ESP32-WROOM.
- Last-peer reconnect.
- Runtime BT MAC in `reply02`.
- Safer UI connection state handling.
- Serial ACK splitting.
- Tests and firmware builds verified.

Result:
This baseline can be used as a known-good reference before future modifications.
